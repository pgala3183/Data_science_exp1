# Associative Pattern Mining — Market Basket (Experiment 4)

Mine frequent itemsets with **Apriori** and **FP-Growth**, derive association rules (support / confidence / lift), and explore them in a force-directed graph, filterable table, and basket add-on simulator.

## Problem statement

Retailers want “customers who bought X also bought Y” recommendations grounded in transaction evidence. Association rules quantify those co-purchase patterns without needing labeled outcomes.

## Dataset & source

Synthetic baskets with planted affinity groups (breakfast, Italian, BBQ, movie night, baby, cleaning) plus bridge pairs — generated by `data/fetch_data.py`. Optionally drop `data/raw/baskets.csv` with an `items` column (semicolon-separated SKUs).

```bash
python data/fetch_data.py --n-baskets 4000
```

## Methodology

1. One-hot encode baskets (`mlxtend.TransactionEncoder`).
2. Run **both** Apriori and FP-Growth at the same `min_support`; record wall-clock and itemset counts.
3. Generate association rules from the FP-Growth itemsets (default serving path).
4. Expose filtered/sorted rules, a lift-weighted item graph, and basket recommendations (consequents of rules whose antecedents ⊆ basket).

## Apriori vs FP-Growth — runtime / memory tradeoff

| | **Apriori** | **FP-Growth** |
|--|-------------|---------------|
| Idea | Level-wise candidate generation + support pruning | Compress baskets into an FP-tree, mine without candidates |
| CPU | Slower when many frequent itemsets / wider baskets (candidate explosion) | Usually faster on sparse retail-like data |
| Memory | Holds large candidate sets in RAM | Tree can be memory-heavy for dense data, but typically leaner for sparse baskets |
| This project | Benchmarked on every `/rules` load (startup mine) | **Default** itemsets used for rules |

On the default ~4k synthetic baskets / ~30 SKUs, FP-Growth is typically **as fast or faster** than Apriori with similar itemset counts; timings are returned in `benchmarks` on `/rules` and shown under the rules table. Scale to Instacart-sized catalogs and Apriori’s candidate generation becomes the bottleneck first — that is why FP-Growth is the serving default.

## How to run

Ports (experiment **4**): API **8004**, UI **5177**.

```bash
python data/fetch_data.py

cd backend
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload --port 8004

cd frontend
npm install
npm run dev
```

Open http://localhost:5177.

### Tests

```bash
cd backend
pytest
```

## API

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/rules` | Paginated rules + algorithm benchmarks |
| `GET` | `/graph` | Nodes/edges for the co-purchase network |
| `POST` | `/recommend` | Top add-ons for a basket |
| `GET` | `/items` | Catalog for the simulator |

## Key result

Strong lift rules recover planted themes (e.g., pasta ↔ tomato sauce, diapers ↔ baby wipes). The basket simulator surfaces those consequents when you seed a partial theme.
