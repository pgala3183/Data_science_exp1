# NYC Taxi Trip Duration Prediction (Experiment 1)

CRISP-DM regression project that predicts **NYC yellow-taxi trip duration** from pre-trip information only: pickup/dropoff coordinates, pickup timestamp, and passenger count.

## Problem statement

Given where and when a trip starts (and where it will end), estimate how long the ride will take. Duration drives ETA, dispatch, and pricing analytics. The hard part is building features and evaluation that do **not** peek at post-trip information.

## Dataset & source

| Mode | Source |
|------|--------|
| **Default** | Synthetic sample generated by `data/fetch_data.py`, schema-aligned with the Kaggle [NYC Taxi Trip Duration](https://www.kaggle.com/c/nyc-taxi-trip-duration) competition |
| **Optional** | Place Kaggle `train.csv` at `data/raw/train.csv` (or pass `--kaggle-csv`) and re-run the fetch + train steps |

Raw/processed files are **gitignored**. Always regenerate locally:

```bash
python data/fetch_data.py
# or with Kaggle file:
python data/fetch_data.py --kaggle-csv data/raw/train.csv
```

## CRISP-DM methodology

1. **Business understanding** — Predict `trip_duration` (seconds) for ETA-style use.
2. **Data understanding** — Coordinates, timestamp, passenger count; target is duration.
3. **Data preparation** — Haversine distance, hour, day-of-week, weekend + rush-hour flags, KMeans pickup/dropoff clusters (**fit on train only**), time-based split.
4. **Modeling** — Ridge baseline + `HistGradientBoostingRegressor`.
5. **Evaluation** — RMSE / MAE / R² on the **later** time holdout.
6. **Deployment** — FastAPI `/predict` + React/Leaflet UI.

### Features (all knowable at request time)

- `haversine_km`, `hour`, `day_of_week`, `is_weekend`, `is_rush_hour`
- `passenger_count`
- `pickup_cluster`, `dropoff_cluster` (KMeans on lat/lon)
- raw coordinates (for local spatial signal)

### How leakage was avoided

Documented explicitly because taxi data is a classic leakage minefield:

| Risk | Mitigation |
|------|------------|
| **Random train/test split** | **Time-based split**: sort by `pickup_datetime`; earlier → train, later → test. Future traffic patterns cannot leak into training metrics. |
| **Using the target as a feature** | `trip_duration` is never in `FEATURE_COLUMNS`. |
| **Post-trip fields** | No `dropoff_datetime`, fare, tip, tolls, speed, or “actual route time” features. |
| **Cluster leakage** | KMeans for pickup/dropoff zones is **fit only on the training window**; the test set and `/predict` only call `predict()`. |
| **Target-driven cleaning on test** | Duration range filters remove impossible labels globally before the split; we do **not** create features from duration statistics of the test fold. |

Speed implied by `distance / duration` would be pure leakage — it is **not** used.

## How to run

Ports (portfolio convention for experiment **1**): API **8001**, UI **5174**.

```bash
# 1) Data
python data/fetch_data.py

# 2) Backend
cd backend
python -m venv .venv
# Windows:
.\.venv\Scripts\activate
pip install -r requirements.txt
# optional explicit train:
python -m app.train
uvicorn main:app --reload --port 8001

# 3) Frontend (new terminal)
cd frontend
npm install
npm run dev
```

Open http://localhost:5174 — Vite proxies `/api/*` → `http://localhost:8001/*`.

On first API startup, if artifacts are missing, the app trains automatically.

### Tests & lint

```bash
cd backend
pytest
ruff check app tests
```

## API

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/health` | Liveness |
| `GET` | `/model/metrics` | Holdout RMSE/MAE/R² + feature importances |
| `POST` | `/predict` | Duration prediction + residual-based 95% interval |
| `POST` | `/model/retrain` | Rebuild artifacts |

```json
{
  "pickup_latitude": 40.758,
  "pickup_longitude": -73.9855,
  "dropoff_latitude": 40.6413,
  "dropoff_longitude": -73.7781,
  "pickup_datetime": "2016-03-15T08:30:00",
  "passenger_count": 1
}
```

## Key result / metric

After `python data/fetch_data.py` and training, check `/model/metrics` (or the UI metrics panel). Typical synthetic-data outcome: **gradient boosting beats Ridge on RMSE**, with **haversine distance** among the top contributors. Exact numbers depend on the generated sample / Kaggle subset — the important claim is that metrics come from a **time-ordered holdout**, not a shuffled split.
